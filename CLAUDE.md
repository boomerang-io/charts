# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Helm v3 charts for Boomerang-io projects, published to the Helm repo at
`https://raw.githubusercontent.com/boomerang-io/charts/index`. There is no application code here, only
chart source. Containers come from DockerHub (`boomerangio/*`).

| Chart | Type | Notes |
|---|---|---|
| `bmrg-common` | library | Shared helper templates (`templates/_boomerang.tpl`). Consumed by every other chart as a dependency with alias `ch`. |
| `bmrg-flow` | application | Boomerang Flow v5 (service-core, service-dispatcher, client-web). Actively maintained. |
| `bmrg-bosun` | application | Boomerang Bosun (app + service + OPA sidecar deployment). |
| `bmrg-auth-proxy` | application | **Deprecated** fork of oauth2-proxy. Do not add features; upstream oauth2-proxy chart is used instead. |

`examples/` holds sample `values.yaml` overrides for Flow installs (basic auth, GitHub auth).

## Commands

Dependencies are not vendored (`charts/` and `Chart.lock` are absent and not tracked), so fetch them first.

```sh
helm dependency update bmrg-flow        # pulls bmrg-common + oauth2-proxy into bmrg-flow/charts/
helm lint bmrg-flow
helm template test bmrg-flow            # render with default values
helm template test bmrg-flow -f examples/flow-github-auth-values.yaml
helm template test bmrg-flow --set general.enable.debug=true -s templates/configmap.yaml   # single template
helm package bmrg-flow
```

Avoid committing the `charts/` dir or `Chart.lock` that `helm dependency update` creates. Run it in a
scratch copy, or clean up after.

Known: `helm lint bmrg-common` fails on `.Release.Time` in `bmrg.util.time` (removed in Helm v3). This is
pre-existing and does not block the application charts.

## Release and publishing model

- The `main` branch is chart source. The protected `index` branch holds only `index.yaml` and is written by
  CI (Boomerang CICD inside IBM, per README), not by hand. `index.yaml` is gitignored on `main`.
- Packaged `.tgz` files live on GitHub Releases, tagged `<chart>-<version>` (e.g. `bmrg-flow-5.5.4`), and
  `index.yaml` points at those release URLs.
- Every change to a chart therefore requires bumping `version` in that chart's `Chart.yaml`, or CI will not
  publish a new artifact. Bump `appVersion` only when the deployed application version changes.
- Application charts depend on a **published** `bmrg-common` version pinned in their `Chart.yaml`
  (Flow pins 3.0.2, Bosun 3.0.1, while local `bmrg-common` is 3.0.4). Editing `_boomerang.tpl` locally
  does nothing for Flow/Bosun until `bmrg-common` is released and the dependency version is bumped.
  To test helper changes locally, temporarily point the dependency `repository` to
  `file://../bmrg-common`, and revert before committing.

## Template architecture

All templates follow one pattern driven by the `bmrg-common` helpers:

1. Each template opens by declaring `$platform := "bmrg"`, `$product := "<flow|bosun|auth>"`, and a
   `$tier` (e.g. `apps`, `services`, `config`, `secrets`, `rbac`, `util`, `opa`, `api`, `app-api`).
2. Resource names come from `include "bmrg.name" (dict "context" $ "tier" $tier "component" $k)`, which
   yields `<namePrefix>-<tier>-<component>`. `namePrefix` defaults to `general.namePrefix` (falling back
   to the release name). Any template referencing another resource must build the name the same way,
   never hard-code it.
3. Labels come from `bmrg.labels.chart` (top-level metadata) and `bmrg.labels.standard`
   (selector/matchLabels, including `zone`). Keep selectors and pod labels using the same helper call.
4. Deployments, Services and Ingresses for `apps` and `services` tiers are generated by ranging over
   `.Values.apps` / `.Values.services`. Adding a new microservice is mostly adding a key under
   `services:` in `values.yaml`; per-component special cases are `if eq $k "<name>"` branches inside the
   loop (e.g. Flow's `workflow` gets encryption secrets, `agent` gets a ServiceAccount).
5. Resources, nodeSelector, affinity, tolerations, Jaeger sidecars and nginx auth-proxy ingress
   annotations all go through the `bmrg.*` helpers rather than inline YAML. See `bmrg-common/README.md`
   for the full helper table.

### Flow-specific wiring (chart 6.x, Flow v5)

- Three components, one product tag: `core` (service-core, port 7700), `dispatcher` (service-dispatcher,
  port 7702) and `web` (client-web, port 3000). Image tags fall back to `image.tag`, then
  `.Chart.AppVersion`, via the `flow.image` helper in `templates/_helpers.tpl`. Bump `appVersion` to move
  the product line.
- Everything is configured by environment, not a ConfigMap. Any `application.properties` key maps to an
  env var by Spring relaxed binding (`flow.encrypt.secret` is `FLOW_ENCRYPT_SECRET`); `core.env`,
  `dispatcher.env` and `web.env` pass arbitrary extras.
- There is no loader Job. service-core migrates MongoDB as it starts and serves nothing until done, so
  `deployment-core.yaml` has a long `startupProbe` and rolls one pod at a time. The images have no shell:
  probes must be `httpGet`.
- `secrets.yaml` generates and preserves (via `lookup`) the encryption pair, the `bfg_` bootstrap token
  and the activation code (`FLOW_ACTIVATION_CODE`). The bootstrap token is both service-core's bootstrap credential and the dispatcher's
  `FLOW_ENGINE_DISPATCHER_TOKEN`.
- The dispatcher's service-core address is one full URL in `FLOW_ENGINE_URL`, defined once in the
  `flow.dispatcher.engineUrlEnv` and `flow.dispatcher.engineUrl` helpers (flow#755). Its RBAC lives in `rbac-role-dispatcher.yaml` and mirrors
  the fabric8 calls in the Flow repo; the Tekton rule is gated on `dispatcher.executor` (default
  `kube-jobs`).
- Ingress: `ingress-web.yaml` serves `/apps/flow` (base path built into client-web, cannot be prefixed)
  with the proxy-auth annotations when `global.auth.enabled`; `ingress-api.yaml` exposes `/api/v2` (and
  `/api/docs` with apidocs) under `global.ingress.root`, never behind the proxy.
- Sign-in is native OIDC. `core.auth.oidc.*` seeds the issuer and client id on first start (flow#831);
  afterwards they live in Flow settings. Proxy sign-in (oauth2-proxy, for
  non-OIDC providers) works because client-web's server forwards `X-Forwarded-Email`/`User`/`Authorization`
  to service-core's auth exchange. MongoDB TLS passes the PEM CA as a Spring SSL bundle, no keytool.
- `oauth2proxy.*` configures the upstream oauth2-proxy subchart (alias `oauth2proxy`,
  `condition: oauth2proxy.enabled`); `configmap-oauth2.yaml` supplies a Carbon-styled custom sign-in
  template to it. The sign-in HTML is itself a Go template, so it is wrapped in a raw-string literal
  (backticks inside the action) so Helm passes it through unrendered.
- Database, ingress and auth settings live under `global.*` so a parent chart can override them.
